## 🧩 書く前に② 属性に、モンスターを入れられる

これまでの属性は、名前（文字）や HP（数）だった。
でも属性には、**モンスターの入ったリスト** を入れることもできるよ。

```python
class Trainer:
    def __init__(self, name):
        self.name = name
        self.team = []          # ← モンスターを入れるチーム表
```

```text
  mina（トレーナー）
   ├─ name → "ミナ"
   └─ team → チーム表
               ├─→ 🟦 ピコ
               └─→ 🟩 ガブ
```

これが、**「トレーナーは、モンスターを持っている」** という関係だよ。

> 🎒 ランドセルと教科書みたいなもの。
> 「ランドセル **は** 教科書だ」は、おかしいよね。
> 「ランドセル **は** 教科書を **持っている**」が、ぴったり。
> トレーナーも、「モンスターである」ではなく、「モンスターを持っている」なんだ。

チーム表に入っているのは、第07章で話した **名札**。
トレーナーはモンスターを誕生させたわけではなく、**すでにいる本人を、チーム表に入れて持っている** んだよ。

### ドットは、左から順に「〜の」と読む

```python
mina.team[0].name
```

左から読むと、「**ミナの**、**チームの**、**1番目の子の**、名前」。
ドットがいくつ続いても、左から1つずつ読めば迷わないよ。

## 🔍 書く前に③ チーム表は、`__init__` の中で作る

事件の答えは、ここにあるよ。

```python
class BrokenTrainer:
    team = []                     # ❌ 設計図に、チーム表を1つだけ書いた
```

`team = []` を `__init__` の **外**（設計図の上の方）に書くと、
チーム表は **設計図に1つだけ** 作られる。
ミナもリョウも、その **同じ1つのチーム表** を使ってしまうんだ。

```python
class Trainer:
    def __init__(self, name):
        self.team = []            # ⭕ 誕生するたびに、新しいチーム表を作る
```

`__init__` は、トレーナーが1人誕生するたびに動く「誕生セット係」だったね。
その中で `self.team = []` と書けば、**トレーナーごとに、別々のチーム表** ができるよ。

> 💡 第07章の言葉で言うと、事件のミナとリョウは「同じ1つのチーム表」に、名札をつけていたんだ。

## 🔍 書く前に④ トレーナーは号令、仕事はモンスター

トレーナーが「みんな、ごはん！」と号令をかけたら、どうなる？

```python
def care_all(self, amount):
    for member in self.team:
        member.eat(amount)        # 食べ方は、モンスター自身が知っている
```

トレーナーは、**だれにごはんをあげるか**（自分のチーム）を知っている。
モンスターは、**どうやって食べるか**（HP の上限ルール）を知っている。

トレーナーの設計図に、HP の計算やルールを書く必要はない。
第08章と同じく、**仕事はそれを知っている子に頼む** んだ。

## 📇 ことばカード

| ことば | 意味 | この章では |
|---|---|---|
| 持っている（has-a） | オブジェクトが、属性として別のオブジェクトを持つ関係 | トレーナーは、モンスターを持っている |
| コンポジション | オブジェクトを組み合わせて作ること | `Trainer` と `Monster` を組み合わせる |
| チーム表 | トレーナーごとのモンスターのリスト | `self.team` |
| 号令 | まとめて頼むメソッド | `mina.care_all(3)` |

## 💡 書いた後に: 何が起きたの？

### 事件の解決: チーム表が、1人に1つになった

`self.team = []` を `__init__` の中に書いたので、
ミナが誕生した時にミナのチーム表、リョウが誕生した時にリョウのチーム表が作られた。
だから、ミナがスカウトしても、リョウのチームは空きのままだったね。

### 2つのクラスが、協力して動いた

```text
mina.care_all(3)                     トレーナーへの号令
 └ for member in self.team:          ミナのチーム表を、上から順に
     └ member.eat(3)                 その子に頼む（eat の中の self は、その子）
```

`Trainer` の中に、HP の計算は1行もない。
それでも、HP の上限ルールはちゃんと守られた（満タンのポポは 10 のまま）。
ルールを知っているのはモンスター。トレーナーは、**頼んだだけ** なんだ。

### 先鋒の交流戦は、第08章の `play_with`

最後の交流戦では、`ranch_tools.py` の道具が、こう呼んでいるよ。

```python
mina.team[0].play_with(ryo.team[0])
```

「ミナのチームの1番目の子が、リョウのチームの1番目の子と遊ぶ」。
第08章で作ったメソッドが、そのまま使えたね。
クラスを組み合わせると、前に作った部品を、新しい場面でどんどん使えるんだ。

<details>
<summary>🎁 おまけ: 「クラス属性」って何？（クリックで開く）</summary>

事件のコードの `team = []` のように、`__init__` の外（クラスのすぐ下）に書いた属性を、
**クラス属性** と呼ぶよ。クラス属性は、その設計図から生まれた **全員で共有** される。

```python
print(BrokenTrainer.team)      # 設計図そのものが、チーム表を持っている
print(vars(broken_ryo))        # {'name': 'リョウ'} ← リョウ自身は team を持っていない！
```

第06章の `vars()` で見ると、リョウ自身は `team` を持っていないことが分かる。
`broken_ryo.team` と書くと、Pythonは「リョウが持っていないなら、設計図のを見よう」と、
みんなで共有している設計図のチーム表を見に行ってしまうんだ。

みんなで同じ値を使いたい時（たとえば、ずっと変わらない数）には便利なこともある。
でも、**1人ずつ別々に持ちたいもの** は、`__init__` の中で `self.〇〇 = ...` と作ろう。

</details>

def recruit(self, monster):
